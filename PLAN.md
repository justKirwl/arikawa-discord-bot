# PLAN.md: Discord-бот «Кінотеатр» (фільми та аніме)

> Єдине джерело правди про план розробки. Його читають і люди, і AI-агенти. Код, коментарі в коді, назви комітів: англійською. Цей план і обговорення: українською.

---

## 0. Суть проєкту

Discord-бот для спільного перегляду фільмів та аніме. Бот керує сеансом (пошук, черга, голосування, розклад), а відео відтворює синхронізований веб-плеєр (Discord Activity або звичайне посилання).

### Жорсткі обмеження (не обговорюються)

1. Бот **не** транслює відео в голосовий канал (селфботи порушують ToS Discord).
2. Лише легальні джерела відео: власні файли учасників або ліцензований/вільний контент. Жодних піратських джерел у коді, конфігах чи документації.
3. Rust-сервіси **нічого не знають про Discord**: лише `room_id`, `user_id`, `media_id` і стан відтворення.
4. Контракти між сервісами (`/proto`, протокол WebSocket) змінюються **першими**, до коду.
5. Жодних секретів у репозиторії (токени, ключі лише через змінні середовища).
6. Принцип розподілу: **Go керує (control plane)**: команди, права, БД, зовнішні API, де затримку визначає мережа. **Rust обробляє (data plane / hot path)**: реальний час, байти відео, медіа-пайплайн, де важливі CPU, пам'ять і стабільні затримки.

## Хто що робить

> Принцип: **Go керує** (Discord, права, база, зовнішні API), **Rust обробляє** (стан кімнат у реальному часі, байти відео, медіа-пайплайн). Бот лишається на Go, бо майже весь час чекає на Discord, Postgres і TMDB: швидкість мови там майже нічого не дає, а ліміти Discord вужчі за будь-який CPU. Контракти та інтеграцію робимо разом. ## 2. Контракти

### 2.1 gRPC (Go ↔ Rust)

`RoomService`:

- `CreateRoom(guild_id, channel_id, host_user_id) → room_id`
- `CloseRoom(room_id)`
- `GetRoomState(room_id) → RoomState`
- `SetMedia(room_id, media_ref)`
- `StreamRoomEvents(stream) → ParticipantJoined | ParticipantLeft | MediaEnded | RoomClosed`

`MediaService` (Go → `mediad`): `GetMediaStatus(media_id)`, `GetPlaybackRef(media_id) → MediaRef`, `DeleteMedia(media_id)`, `StreamMediaEvents(stream) → TranscodeProgress | MediaReady | MediaFailed`. Самі байти файлу йдуть не через gRPC, а по HTTP: браузер → `mediad` з токеном завантаження.

### 2.2 WebSocket (браузер ↔ Rust)

Клієнт → сервер: `join{token}`, `play`, `pause`, `seek{position_ms}`, `ping{client_ts}`. Сервер → клієнт: `state{version, media_ref, position_ms, playing, server_ts}`, `participants`, `pong{client_ts, server_ts}`, `error{code}`.

### 2.3 Модель стану та формула синхронізації

Сервер зберігає: `media_ref`, `position_ms`, `playing`, `updated_at_server_ms`, `version`.

Очікувана позиція на клієнті:

- пауза: `position_ms`
- відтворення: `position_ms + (server_now − updated_at_server_ms)`

`server_now` клієнт оцінює через `ping/pong` (зсув годинника). Якщо розбіжність більше **500 мс**, плеєр робить seek. Менші відхилення можна гасити невеликою зміною `playbackRate`.

### 2.4 Авторизація кімнати

Go видає короткоживучий токен (JWT, підпис Ed25519). Rust перевіряє його публічним ключем. Claims: `room_id`, `user_id`, `role` (host/viewer), `exp`.

Для завантаження файлів діє той самий механізм: токен із claims `user_id`, `guild_id`, `max_bytes`, `exp`. `mediad` перевіряє його сам, байти йдуть повз Go.

### 2.5 Модель даних (Postgres)

> Схема належить Go-розробнику (`services/bot`), міграції через goose (S1.2). Rust-сервіси Postgres не чіпають: стан кімнат живе в пам'яті `roomd`, кеш метаданих у Redis, JWT-токени ніде не зберігаються.
>
> Три таблиці (`guild_settings`, `session_items`, `media_files`) додано до початкового списку, бо без них не закрити S1.5/S7.5, S7.2–S7.3 та S4.2a. Поле `host_user_id` у `sessions` теж нове: його вимагає `CreateRoom` (2.1).

**Загальні правила**

| Тема | Правило |
| --- | --- |
| Імена | `snake_case`, таблиці у множині, первинний ключ завжди `id` |
| ID з Discord (user, guild, channel, role, message) | `BIGINT` (snowflake вміщується в знаковий int64, у Go це `int64`) |
| Внутрішні ID | `BIGINT GENERATED ALWAYS AS IDENTITY` |
| ID для інших сервісів (`room_id`, `media_id`) | `UUID`. Формат `room_id` у `proto/` має бути `string` з UUID (узгодити в S0.2) |
| Час | `TIMESTAMPTZ`, у UTC. Колонки `created_at` / `updated_at` скрізь `NOT NULL DEFAULT now()` |
| Enum-и | `TEXT` + `CHECK (... IN (...))`, а не `CREATE TYPE ... ENUM`: простіше змінювати міграціями |
| Зовнішні ключі | `ON DELETE RESTRICT`. Виняток: `guild_settings`, `session_items`, `votes` мають `CASCADE`. `guilds` і `users` фізично не видаляємо (бот вийшов із сервера = `guilds.left_at`) |

**Зв'язки** (стрілка = зовнішній ключ)

```
guilds ─┬─ guild_settings        (1:1)
        ├─ queue_items ───► titles, users (added_by)
        ├─ sessions ──┬─ session_items ───► titles
        │             └─ votes ───► users, titles
        ├─ ratings ───► users, titles
        └─ media_files ───► users (uploader)
users ─── watchlist_items ───► titles
```

| Поле | Тип | Обмеження | Опис |

| `guild_id` | `BIGINT` | NOT NULL, FK → `guilds.id` | Сервер |
| `channel_id` | `BIGINT` | NOT NULL | Discord-канал, де запущено `/watch`. Окремої таблиці каналів немає |
| `host_user_id` | `BIGINT` | NOT NULL, FK → `users.id` | Хост (аргумент `CreateRoom`) |
| `message_id` | `BIGINT` | NULL | Повідомлення з кнопкою «Приєднатися» (S6.2). `NULL`, доки не опубліковано |

| `ended_at` | `TIMESTAMPTZ` | NULL | `NULL` = сеанс триває. Ставиться по `RoomClosed` |

Ключі та індекси: `UNIQUE (channel_id) WHERE ended_at IS NULL` (один активний сеанс на канал), `INDEX (guild_id, started_at DESC)` для `/history`.

#### `session_items` (S7.2, S7.3)

Що саме дивилися протягом сеансу. В одному сеансі може бути кілька тайтлів поспіль.

| Поле | Тип | Обмеження | Опис |

#### `media_files` (S4.2a, лише якщо D1 включає власні файли)

Облік завантажень для квот. Рядок створює Go під час видачі токена завантаження; `mediad` до Postgres не звертається, статус оновлюється з подій `StreamMediaEvents`.

| Поле | Тип | Обмеження | Опис |
| --- | --- | --- | --- |
| `id` | `UUID` | PK | `media_id`; Go генерує його при видачі токена |
| `guild_id` | `BIGINT` | NOT NULL, FK → `guilds.id` | Сервер, на чию квоту йде файл |
| `uploader_id` | `BIGINT` | NOT NULL, FK → `users.id` | Хто завантажує |
| `original_filename` | `TEXT` | NOT NULL | Ім'я файлу від користувача (за замовчуванням стає `titles.title`) |
| `reserved_bytes` | `BIGINT` | NOT NULL, CHECK > 0 | Зарезервоване місце = `max_bytes` із токена |
| `size_bytes` | `BIGINT` | NULL | Фактичний розмір. Заповнюється після `MediaReady` (поля події узгодити в `proto/`) |
| `duration_ms` | `BIGINT` | NULL | Тривалість відео. Заповнюється після `MediaReady` |
| `status` | `TEXT` | NOT NULL, DEFAULT `'pending'`, CHECK IN (`'pending'`, `'transcoding'`, `'ready'`, `'failed'`, `'deleted'`) | `pending` = токен видано, файл ще не прийшов; `transcoding` = перша `TranscodeProgress`; `ready` / `failed` = `MediaReady` / `MediaFailed`; `deleted` = після `DeleteMedia` |
| `error` | `TEXT` | NULL | Причина, якщо `failed` |
| `upload_expires_at` | `TIMESTAMPTZ` | NOT NULL | Коли спливає токен завантаження. `pending`-рядки після цього моменту не враховуються в квоті й підлягають очищенню |
| `created_at` | `TIMESTAMPTZ` | NOT NULL | Коли видано токен |
| `updated_at` | `TIMESTAMPTZ` | NOT NULL | Остання зміна статусу |

Ключі та індекси: `INDEX (guild_id, status)`, `INDEX (uploader_id, status)`. Використане місце = сума `COALESCE(size_bytes, reserved_bytes)` за рядками зі статусами `pending` (не прострочені), `transcoding`, `ready`.

Коли файл стає `ready`, Go створює рядок у `titles` з `source = 'custom'`, `external_id = media_files.id`, і далі він працює в черзі й сеансах як будь-який інший тайтл.

**Припущення, які треба підтвердити**

1. Watchlist особистий (по `user_id`), черга спільна на сервер (по `guild_id`).
2. Один тайтл може бути в черзі сервера лише один раз.
3. Шкала оцінок 1–10; оцінка прив'язана до сервера, тож той самий користувач може оцінити тайтл по-різному на різних серверах.
4. Один активний сеанс на Discord-канал.
5. `/schedule` (S6.5) таблиці не має: подію зберігає сам Discord. Якщо потрібні нагадування, що переживають рестарт бота, додамо `scheduled_events`.
